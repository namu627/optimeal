# 식단가 이월(기간 총액) 예산 — 규칙·근거·한계

작성 2026-10-01 · 코드: `module_3/src/budget_carryover.py`, `module_4/backend/src/routers/menu.py`(`CARRYOVER_GUARD`),
프론트 `module_4/frontend/src/api/menu.ts`(`budgetSummary`·`checkSwap`)

현장 식단가는 "기간 총액 안에서 어떤 날은 조금 비싸고 어떤 날은 조금 싸게" 운영한다. 예전 하루 상한
(`budget_period="day"`)은 하루라도 B×M 을 넘어야 하면 전체가 INFEASIBLE 이었다. 이월 모드는 **기간 총액만
Hard** 로 두고, 한 끼 몰아쓰기·최저가 쏠림은 끼니 울타리(Hard)와 밴드(Soft)로 막는다.
화면 기본값은 이월(`budget_mode="carryover"`)이고, Step1 에서 '하루 기준'으로 바꿀 수 있다.

기호: **B** = 1인 1끼 예산(원) = 하루 예산 ÷ 끼니 수, **M** = 하루 끼니 수, **D** = 일수.

## 1. 규칙

| 규칙 | 종류 | 값 | 위반 시 |
|---|---|---|---|
| 기간 총예산 | **Hard** | 1인 총원가 ≤ B×M×D (`budget_period="total"`) | 해 없음 |
| 끼니 원가 울타리 | **Hard** | 모든 (날짜, 끼니) 1인 원가가 B×0.7 이상 B×1.3 이하 | 해 없음 → 울타리를 풀고 다시 풂(`stop_reason="guard_relaxed"`, 화면 안내) |
| 끼니 밴드 | Soft | B×0.8 ~ B×1.2 | 벗어난 100원당 −2 (`w_band=2`) |
| 연속일 원가 균형 | Soft | 같은 끼니 슬롯의 전날 대비 원가 차 ≤ B×0.25 | 초과 100원당 −1 (`w_smooth_cost=1`) |
| 연속일 나트륨 균형 | Soft | 전날 대비 하루 나트륨 합 차 ≤ 나트륨 상한×0.25 | 초과 100mg당 −1 (`w_smooth_sodium=1`, 상한을 줄 때만) |

- 울타리는 **증명된 INFEASIBLE** 일 때만 푼다(시간 초과 UNKNOWN 은 풀지 않음). 재풀이에 최소 10초를 보장한다.
- 교체(Step2)도 같은 규칙을 지킨다: 후보 API 가 `within_total_budget`·`within_meal_guard` 를 돌려주고,
  화면 `checkSwap` 이 총예산·울타리를 넘는 교체를 막는다.
- 원가는 접시별로 100원 단위 정수로 선형화해 모델에 넣고, 리포트·화면 합계는 반올림 전 원 단위(`cost_exact`)로 다시 더한다.

## 2. 근거

읽는 법:
- **어떤 조합도 밴드 밖 끼니를 15%(3/21) 이하로 못 내렸다.** 최저 6.0끼(29%)도 2회 중 1회가 UNKNOWN 이다.
- 최저 끼니는 0.3~0.6B, 최고 끼니는 1.3~1.7B 가 남는다. 30초 안에 Soft 벌점이 해를 충분히 밀지 못한다.
- 가중치를 올려도 개선이 일관되지 않고, 같은 조합 2회 사이 차이(예: 0/0 총원가 64,073 vs 68,512)와 비슷한
  크기다. 반면 Soft 항을 켜면 제철 점수가 5~12% 줄고(0/0 대비), 일부 조합은 UNKNOWN 을 낸다.
- 그래서 **극단은 Hard 울타리(2.2)로 자르고, Soft 는 가장 작은 가중치(2/1)** 로 남겼다. 두 번 모두 FEASIBLE 이고,
  울타리 안에서 밴드·연속일 균형을 가볍게 당기는 역할만 한다.

- 0.5~1.5·0.6~1.4 는 극단은 줄지만 밴드 밖 끼니가 없음 수준(9~11/21)으로 남는다.
- 대가는 총원가다. 하한 0.7B 가 싼 끼니를 끌어올려 7일 3식 B=3,500 총원가가 약 5% 오른다(평균 69.4k → 72.7k).

  나빠졌다. 그래서 Soft 균형은 남겼다.
- 0.7 보다 좁은 울타리(예: 0.8~1.2 를 Hard 로)는 이 스윕에서 측정하지 않았다. 좁힐수록 guard_relaxed 로 떨어질
  가능성이 커지므로, 바꾸려면 위 시나리오로 다시 스윕한다(`CARRYOVER_GUARD`).

## 3. "맛 균형"을 원가 + 나트륨으로 정의한 이유

- 맛·선호를 직접 재는 데이터가 없다. 후보 메뉴의 `preference` 는 전부 0이고, 기호도 조사도 아직 없다.
  **데이터에 있는 메뉴 단위 수치 중 연속일 체감과 연결되는 것**만 골랐다.
- **나트륨**: 하루 짠맛·양념 세기의 대리 지표다. 전날 짜게 먹고 다음 날 싱거우면 체감 편차가 크다. 하루 상한(Hard)과
  별개로, 연속일 차이를 줄이는 쪽으로만 건다.
- **원가**: 같은 끼니 슬롯에서 '고기·해산물 위주로 푸짐한 날'과 '채소 위주로 가벼운 날'의 대리 지표다. 이월을
  허용하면 원가가 날짜 사이에서 크게 출렁일 수 있어, 그 출렁임을 직접 줄이는 항이 필요하다.
- 조리법·색·재료 반복은 이미 다양성 Soft·반복 금지 Hard 가 따로 다룬다. 균형 항에 다시 넣으면 같은 신호를 두 번
  센다.
- 한계: 대리 지표일 뿐이다. 영양사 피드백이나 잔반 데이터가 쌓이면 교체 대상이다.

## 4. 한계

1. **31일 3식은 지원하지 않는다.** 이월 모드 31일 3식은 80초 안에 UNKNOWN 이 두 번 나왔다(82초·83초).
   그래서 화면에서 31일은 점심만 고를 수 있다. 31일 점심은 FEASIBLE(36~48초).
2. **조식·중식·석식의 1끼 예산이 같다.** B = 하루 예산 ÷ 끼니 수 하나로 울타리·밴드를 건다. 현장에서 조식을 싸게
   잡는 경우는 반영하지 못한다. 끼니별 B 를 받으려면 `CarryoverConfig`·요청 스키마를 끼니별로 확장해야 한다.
3. **원가는 참고 시세다(발주 단가가 아님).** 재료마다 하나의 가격을 아래 출처 우선순위로 고르고, 같은 출처 안에서는
   최신 날짜를 쓴다(`scripts/price_priority.py`, `csp_solver.PRICE_SOURCE_PRIORITY`).
   **KAMIS 도매 > 가락시장(서울시농수산식품공사) > KAMIS 소매 > 참가격 소매 > 수기 참조 > 파생(쌀 환산·상위품목·동의어) > 정책 0원(물·육수)**
   - 가격이 없는 재료는 0원으로 더해진다. 재료 가격 커버리지는 85.5%(2026-10-01)라 일부 메뉴 원가가 실제보다 낮다.
   - 소매·수기 출처가 섞여 있어 도매 기준 원가보다 높게 잡히는 재료가 있다.
4. **식단 생성은 서버 전체에서 동시에 1건.** CP-SAT 이 4코어를 다 쓰므로 `_SOLVE_LOCK` 으로 1건만 푼다. 두 번째
   요청은 3초 기다린 뒤 429(`solver_busy`)를 받는다. 락이 프로세스 단위라 uvicorn 워커는 1개로 둔다.
5. 1인분 재료량의 원본 이상치(예: 무 현미밥 곡물 280g, 배추겉절이 고춧가루 25g)는 원본 값 그대로다. 로더 버그였던
   여러 인분 레시피(2·4인분 44종)는 2026-10-01 에 1인분으로 나눠 다시 적재했다.
   목록: `scripts/check_recipe_serving_outliers.py` → `data/external/recipe_serving_outliers_YYYYMMDD.csv`(70행·65메뉴, 2026-10-01).
