## 1. 문서 개요

### 1.1 목적

본 문서는 OptiMeal 프로젝트의 기능/비기능 요구사항을 체계적으로 정의하고, 각 기능의 입출력 명세, 처리 로직, 검증 기준을 기술한다. 개발팀 전원이 동일한 기준으로 개발 및 테스트를 수행할 수 있도록 한다.

### 1.2 범위

본 문서는 4개 모듈을 다룬다.

- **모듈 1**: 영양성분 DB (식약처 + 식품안전나라)
- **모듈 2**: 비선형 스케일링 엔진 (Rule-based 메인 + ML 보조 하이브리드)
- **모듈 3**: CSP Solver (식단 자동 생성)
- **모듈 4**: Frontend (통합 UI)

### 1.3 용어 정의

| 용어 | 정의 |
|------|------|
| 소규모 레시피 | 1~10인분 기준 레시피 (주로 1인분, 영양사 인증 자료) |
| 대규모 레시피 | 50인분 이상 기준 레시피 (급식소, 산업체 실측 자료) |
| 스케일링 지수 (b) | 멱함수 Y = a × X^b에서의 지수. b=1이면 선형, b<1이면 대량 시 덜 필요 |
| 다층 유사도 | group_type 필터 → 재료 Cosine → 복합 점수의 3단계 매칭 [ADR-002 v5: 가중 Jaccard 제거] |
| Rule-based 엔진 | 통계 분석으로 도출한 스케일링 지수 룩업 테이블 기반 변환 엔진 |
| ML 보조 모듈 | 재료 자동 분류, 미등록 조합 예측을 담당하는 보조 ML 모델 |
| 하이브리드 | Rule-based 메인 + ML 보조를 결합한 최종 스케일링 파이프라인 |
| CSP | Constraint Satisfaction Problem. 제약 충족 문제 |

### FR-01. 비정형 레시피 정규화 엔진

| 항목 | 내용 |
|------|------|
| **ID** | FR-01 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 2 |
| **담당 파트** | Data / Back |
| **관련 테이블** | `unit_conversion`, `ingredient`, `ingredient_synonym`, `recipe_ingredient_map` |

**설명**: OpenAPI 및 수집 레시피의 비정형 텍스트("한 꼬집", "적당량", "양파 반 개" 등)를 표준 단위(g, ml)로 변환하는 결정론적 파서.

**입력**:
- 원본 레시피 텍스트 (재료명 + 분량 + 단위)

**처리 로직**:
1. 재료명 정규화: `ingredient_synonym` 테이블 조회 → 표준 `ingredient_id` 매핑
2. 단위 환산: `unit_conversion` 테이블 조회 → `amount_in_grams` 계산
3. 범용 환산 → 재료별 특수 환산 순서로 적용
4. "적당량", "약간" 등 모호한 표현은 재료 카테고리별 기본값 적용

**출력**:
- `recipe_ingredient_map` 레코드 (amount_in_grams 채워진 상태)

**검증 기준**:
- 정규화 성공률 ≥ 95% (전체 재료 텍스트 중 g 변환 성공 비율)
- `ingredient_synonym` 매칭률 ≥ 90%

### FR-03. 다층 유사도 기반 레시피 매칭

| 항목 | 내용 |
|------|------|
| **ID** | FR-03 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 2 |
| **담당 파트** | Data / AI |
| **관련 테이블** | `recipe`, `recipe_ingredient_map`, `recipe_similarity`, `cooking_method` |

**설명**: 소규모-대규모 레시피를 3단계 다층 유사도 알고리즘으로 매칭. [ADR-002 v5: 2026-03-14, 가중 Jaccard 제거]

**입력**:
- 소규모 레시피 목록 (serving_category='소규모')
- 대규모 레시피 목록 (serving_category='대규모', per_serving_grams 환산 완료)

**처리 로직**:
1. **1단계 — `group_type` 필터링 [ADR-002]**: 동일 `cooking_method.group_type` (3대분류)로 후보군 축소
2. **2단계 — 재료 binary 벡터 Cosine Similarity**: 정규화된 재료 집합을 binary 벡터로 표현 → 코사인 유사도. 기록 상세도 불균형에 강건.
3. **3단계 — 복합 유사도**: 0.4×(메뉴명유사도) + 0.6×(재료Cosine)
   - 메뉴명유사도: `difflib.SequenceMatcher` 기반 부분 일치 (이종 DB 표기 차이 흡수)
4. **수동 검수 [ADR-002]**: 전체 확정 쌍의 30% 이상 직접 동일 메뉴 여부 확인 → `is_manually_verified = TRUE`

> **[ADR-002 v5] 가중 Jaccard 제거 근거**: 소규모(평균 10~18종) vs 대규모(평균 5~13종) 이종 DB 기록 상세도 불균형으로 Jaccard 분모 체계적 과대평가 실증. 전수 스캔(583건) 복합점수 최댓값 0.57 — 임계값 조정으로 해결 불가.
> **재현 스크립트**: `matching_optionB.py` (Python 3.12, pandas 2.x, numpy 1.x, scikit-learn 1.x, difflib 표준 라이브러리)

**파일럿 가중치 민감도 분석**: 초기 20~30쌍 영양사 검수 결과 비교, 복합 유사도 가중치(0.4/0.6) 민감도 측정 → 논문 방법론 근거 자료 확보

**출력**:
- `recipe_similarity` 레코드 (3단계 점수 + 매칭 결정 + `is_manually_verified`)
- `recipe.recipe_group_id` 자동 부여 (확정된 쌍)

**매칭 결정 기준**:
- ≥ 0.7: 자동 태깅
- 0.6 ~ 0.7: 수동 검토
- < 0.6: 제외

**검증 기준**:
- 확정 매칭 쌍 ≥ 150건 (실측 기준: 171쌍 확보 가능 — 자동 71 + 수동검토 100)
- **3대분류별 현황 [ADR-002 v5]**: 습열 82쌍 / 건열 59쌍 / 비가열 30쌍
  - ⚠ 비가열 30쌍은 구 기준(≥50쌍) 미달 — 논문 한계 절 명시 의무 (ADR-002 v5 준수사항 15항)
- is_manually_verified 비율 ≥ 30%

### FR-04. 통계 기반 스케일링 지수 도출

| 항목 | 내용 |
|------|------|
| **ID** | FR-04 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 2 |
| **담당 파트** | AI / Data |
| **관련 테이블** | `scaling_coefficient`, `recipe_ingredient_map`, `ml_training_dataset` |

**설명**: 매칭된 레시피 쌍으로부터 `ratio` 기반 혼합효과 모델(MixedLM)을 주 전략으로, 멱함수 회귀(curve_fit)를 보조 전략으로 스케일링 지수를 직접 도출. [ADR-001, ADR-002]

**핵심 수식 [ADR-001 Option A]**:
- 종속변수: `ratio = 실제 대규모 투입량 / (base_amount × N)` (1에 가까울수록 선형)
- 모델: `ratio = a × N^(b-1)` → 역변환: `Y = a × base_amount × N^b`
- Baseline(기준선): ratio = 1 (b=1 동치, 단순 선형)

**입력**:
- 매칭된 레시피 쌍 150건 이상 (3대분류별 50쌍 이상)
- 각 쌍의 재료별 (base_amount_g, target_amount_g, target_serving_n)
- 사전 계산된 `ratio` 컬럼

**처리 로직**:
1. **EDA [ADR-001]**: `ratio` 종속변수 기준 분포 시각화, 이상치 탐지 (IQR×1.5 기준)
   - 3대분류 × 재료 카테고리별 ratio 분포 시각화
   - 건열 그룹 내 분산(볶음·구이·부침) 허용 범위 점검 [ADR-002]
   - **⭐ v1.3 신규 — ratio 이상치 사전 임계값 (교수 피드백 2.3 반영, ADR-002 v4)**:
     - **사전 임계값**: `ratio < 0.2 또는 ratio > 3.0` (EDA 착수 전 사전 선언, 데이터 확인 후 변경 금지. 도메인 기준 채택 — 2026-03-20 확정)
     - **처리 정책**: 이상치는 분석(MixedLM, curve_fit)에서만 제외. DB 레코드는 삭제하지 않고 보존.
     - **모니터링**: 이상치 비율이 전체 쌍의 10% 초과 시 데이터 수집 품질 재검토. EDA 리포트에 이상치 비율 기재 의무.
2. **MixedLM — 주 전략 [ADR-002]**: statsmodels.MixedLM
   - 설계식: `log(ratio) = log(a) + (b-1)×log(N) + β₁×Category + u_method`
   - 고정효과: log(N), Category (재료 카테고리 5종)
   - 랜덤효과: u_method ~ N(0, σ²) ← 조리방법 3대분류 그룹
   - 수렴 실패 시: REML→ML 전환 시도
   - **⭐ v1.3 신규 — OLS 비교 병행 (교수 피드백 2.2, ADR-002 v4)**: OLS(고정효과 only) 모델과 AIC 비교 실시. AIC_MixedLM < AIC_OLS 확인으로 랜덤효과 도입 정당성 검증.
3. **curve_fit — 보조 전략 [ADR-002]**: scipy.optimize.curve_fit
   - **셀당 N≥10인 조합에만 실행** (그 외 셀은 MixedLM 결과 사용)
   - 모델: `ratio = a × N^(b-1)`, MixedLM 결과와 비교용
   - **⭐ v1.3 신규**: |b_MixedLM - b_curvefit| > 0.1 시에도 MixedLM 값 최우선 채택. 차이 발생 셀 수 및 비율 분석 리포트에 보고 의무. [ADR-002 v4]
4. **교차 검증**: 5-Fold CV로 MixedLM 지수 안정성 확인
5. **유의성 검증**: 선형(b=1, ratio=1) 대비 멱함수 AIC/BIC 비교, p < 0.05
6. **⭐ v1.3 신규 — H0₃ 가설 검정**: 조리방법 대분류 간 b 차이 one-way ANOVA. 4월 통계 완료 후 실시. [ADR-002 v4]

**출력**:
- `scaling_coefficient` 레코드 (version=1, source='통계분석')
  - `estimation_method`: 'mixedlm' 또는 'curve_fit' [ADR-002]
  - `sample_size`: 각 셀 실제 N 기록
  - power_law_a, power_law_b, r_squared, p_value, 신뢰구간 포함

**검증 기준**:
- 모든 스케일링 지수의 p-value < 0.05
- 멱함수 모델의 AIC < 선형 모델의 AIC (Baseline ratio=1 대비 개선 확인)
- **⭐ v1.3 신규**: AIC_MixedLM vs AIC_OLS 비교 결과 분석 리포트에 포함
- **⭐ v1.3 신규**: 비가열 그룹 Power Analysis 수치 (α=0.05, 1-β=0.80, f²=0.15~0.25 가정) EDA 보고서에 포함

### FR-05. Rule-based 스케일링 엔진 (메인)

| 항목 | 내용 |
|------|------|
| **ID** | FR-05 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 2 |
| **담당 파트** | AI / Back |
| **관련 테이블** | `scaling_coefficient`, `ingredient`, `ingredient_synonym`, `cooking_method` |

**설명**: 통계 분석으로 도출한 스케일링 지수 룩업 테이블 기반으로, 소규모 레시피를 목표 인원수에 맞게 변환하는 핵심 엔진.

**입력**:
- 소규모 레시피 (recipe_id)
- 목표 인원수 (target_serving_size)

**처리 로직**:
1. 입력 레시피의 조리방법 분류 → `cooking_method.group_type` 확인 (3대분류: dry_heat/moist_heat/no_heat) [ADR-002]
2. 각 재료를 카테고리별로 분류 (ingredient_synonym → ingredient.category)
3. `v_scaling_lookup` 뷰에서 **(group_type × 재료카테고리)** 키로 파라미터 조회 [ADR-002]
4. 역변환 수식 [ADR-001 Option A]: `Y = power_law_a × base_amount × target_serving^power_law_b`
5. **예외 처리 (Fallback, estimation_method = 'category_mean')**:
   - 1순위: 동일 (group_type × 카테고리) 셀 MixedLM 추정값
   - 2순위: 동일 카테고리 전체 평균 지수
   - 3순위: 전체 데이터 평균 지수
   - 각 단계에 추정 신뢰도 플래그 (high/medium/low)

**출력**:
- 대규모 레시피 (재료별 조정된 투입량 + 신뢰도 플래그)

**검증 기준**:
- Baseline(선형) 대비 MAE 20% 이상 개선
- MAPE < 15%

- **⭐ v1.3 신규 — 오분류 민감도 분석**: 4월 ML 모듈 완성 후, 오분류된 재료명의 스케일링 지수에 미치는 영향(민감도 분석) 수행 의무. "잘못 분류된 재료의 b값 오차가 최종 MAPE에 미치는 영향" 정량 분석.

### FR-09. 영양사 피드백 루프

| 항목 | 내용 |
|------|------|
| **ID** | FR-09 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 2 |
| **담당 파트** | Common |
| **관련 테이블** | `nutritionist_feedback`, `scaling_coefficient` |

**설명**: 영양사가 AI 생성 대규모 레시피를 평가하고, 피드백을 스케일링 파라미터에 반영하는 순환 개선 체계.

**처리 흐름**:
1. 하이브리드 엔진으로 대규모 레시피 생성
2. 영양사 평가 (상용가능 / 수정필요 / 부적합)
3. 재료별 수정 사항을 JSON으로 기록 (`{"고추장": "-100g", "물": "+500ml"}`)
4. **피드백 적용 대상 셀 결정 [ADR-002 v3]**:
   - 해당 `cooking_method_id`의 세부 조리방법 b값이 이미 존재하는 경우 → `(cooking_method_id × ingredient_category)` 셀 업데이트, `estimation_method = 'nutritionist_feedback'`
   - 세부 조리방법 b값이 없는 경우 → `(group_type × ingredient_category)` 3대분류 통계 b값 보정
5. 멱함수 파라미터 a, b를 가중 평균으로 업데이트 (ADR-003 수식 적용)
6. `scaling_coefficient` 새 버전 생성 (`parent_coefficient_id`로 체인, `source = '영양사피드백'`)
7. 총 5회 반복 [ADR-002 v3]:
   - 1회 (건열-볶음) → 2회 (건열-구이·부침 + 습열-끓이기) → 3회 (습열-찜·조림 + 비가열)
   - 4회 (혼합 조리법) → 5회 (전체 재검증)

**피드백 b값 학술적 위상 [ADR-002 v3]**:
- 통계 도출 b (`estimation_method = 'mixedlm'/'curve_fit'`): 방법론적 정당성 담당
- 피드백 보정 b (`estimation_method = 'nutritionist_feedback'`): 현장 적용 가능성 고도화 담당
- 논문 한계 절 기술 의무: "피드백 기반 b값은 재현 가능성이 통계 기반 b값보다 낮으며, 현업 전문가 지식에 의한 보완임을 명시한다."

**루브릭 평가 기준 [ADR-002]**: 5점 척도, 항목별 사전 정의
- ① 맛·간 적절성 (1~5점)
- ② 조리 실현 가능성 (1~5점)
- ③ 대량 조리 현장 적합성 (1~5점)
- 평균 ≥ 4.00 = "상용 가능" 판정

**검증 기준**:
- 동일 조리 그룹에서 연속 10개 레시피의 루브릭 평균 ≥ 4.00점
- 영양사 승인율 ≥ 80%

### FR-11. CSP Solver (식단 자동 생성)

| 항목 | 내용 |
|------|------|
| **ID** | FR-11 |
| **우선순위** | P0 |
| **담당 모듈** | 모듈 3 |
| **담당 파트** | Back / AI |
| **관련 테이블** | `nutrition_recipe`, `user_group`, `constraints` |

**설명**: Google OR-Tools 기반 제약 충족 알고리즘으로 영양균형을 만족하는 7일/31일 식단 자동 생성.

**입력**:
- 타겟 그룹 (user_group)
- 급식 일수 (7일 또는 31일)
- 끼니 수 (1~3끼)

**입력**:
- 타겟 그룹 (user_group): 인원수, 연령대
- 기저질환자 정보: 질환 종류(당뇨/고혈압/신장질환) + 인원수 [ADR-002]
- 알레르기 보유자 정보: 알레르기 항목(식품알레르기 표시제 **22종**) + 인원수 [ADR-002]
- 식단가(1인당 예산, 원): ingredient_price 테이블 연동 [ADR-002]
- 급식 일수 (7일 또는 31일)

**처리 로직**:
- **Hard Constraint**:
  - 하루 칼로리 = 권장량 ± 10%
  - 알레르기 식재료 22종 **완전 배제** (그룹별 적용) [ADR-002]
  - 기저질환 상한: 당뇨(일일 당류), 고혈압(나트륨), 신장질환(칼륨·인) — 한국당뇨병학회·대한영양사협회 가이드라인 [ADR-002]
  - 식단가 예산: 총 식재료비 ≤ 입력 식단가 × 인원수 [ADR-002]
- **Soft Constraint**:
  - 메뉴 중복 회피 (3일 이내 재등장 금지)
  - 끼니별 영양 배분 (아침 30%, 점심 40%, 저녁 30%)
  - 제철 식재료: seasonal_ingredient.freq_score 기반, 포함 비율 ≥ 40% 목표 [ADR-002]
  - 색감 다양성: ingredient.color_category 기준, 한 끼니에 3가지 이상 색상 포함 목표 [ADR-002]
- **Scoring Function**: `Total_Score = (영양점수 × 0.4) + (예산적합도 × 0.3) + (제철·색감 × 0.2) + (다양성 × 0.1)` [ADR-002]
- **대체 메뉴 분기**: 기저질환자·알레르기 보유자를 위한 '공통식 + 대체식' 트랙 분리 [ADR-002]

**출력**:
- 일별 식단표 (공통식 + 대체식 분리, 메뉴 목록 + 영양소 합산)
- 1인 원가 (ingredient_price 연동)

**검증 기준**:
- Hard Constraint 100% 만족 (알레르기·기저질환 오류율 0%)
- 영양사 검수 통과 (이상 조합 없음)
- 연산 시간 < 60초 (31일 기준, 벤치마크 [ADR-002])

- 대체식 정보 (알레르기 제외 시)

## 3. 비기능 요구사항 (Non-functional Requirements)

### NFR-01. 정확성 (Accuracy)

| 항목 | 기준 |
|------|------|
| 스케일링 오차 | 선형 대비 20% 이상 개선, 최종 MAPE < 15% |
| 영양성분 오차 | 표준값 대비 ± 10% 이내 |
| 단위 환산 | LLM 확률이 아닌 표준 환산 테이블 기반 (결정론적) |
| 통계적 유의성 | 모든 스케일링 지수 p-value < 0.05 |

### NFR-02. 성능 (Performance)

| 항목 | 기준 |
|------|------|
| 레시피 스케일링 | 응답 시간 < 3초 |
| 식단 생성 (31일) | 연산 시간 < 60초 |
| 영양성분 검색 | 응답 시간 < 1초 |
| 일반 API 호출 | 응답 시간 < 5초 |

### NFR-03. 데이터 신뢰성

| 항목 | 기준 |
|------|------|
| 소규모 레시피 | 영양사 인증 / 정부기관 공인 자료 |
| 대규모 레시피 | 산업체 실측 / 영양사협회 서적 / 영양사 커뮤니티 검증 자료 |
| 합성 데이터 | 사용하지 않음 |
| 스케일링 지수 | 직접 통계 분석으로 도출 (LLM 미사용, 학술적 재현성 확보) |

### NFR-04. 플랫폼 및 배포

| 항목 | 기준 |
|------|------|
| 플랫폼 | 웹(Web) 기반, 별도 설치 불필요 |
| 백엔드 | FastAPI + PostgreSQL/MySQL |
| 프론트엔드 | React (Vite) |
| 컨테이너 | Docker 기반 배포 |
| **라이브러리 버전 고정** | `requirements.txt` (scipy·statsmodels·scikit-learn 버전 명시) + Docker 이미지 태그 기록 — **학술적 재현성 확보** ⭐ v4.0 |

### NFR-05. 학술적 요구사항

| 항목 | 기준 |
|------|------|
